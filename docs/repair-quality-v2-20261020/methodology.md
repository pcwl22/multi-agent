# 质量策略 V2：有限追加校准

首轮 72 次对照严格成功为旧行为 26/36、质量策略 V1 21/36，主指标下降。全部失败、原始候选及记录保留在 `../repair-quality-20261020/`。该结果不能表述为修复成功率提升。更早历史评测 17/24 保持不变。

本轮先固定实现，再冻结预注册、已验证 wheel、同一语料锁和镜像，最后才开始真实模型任务。六个案例全部已经观察；它们是校准回归集，不是新的未见缺陷或未见项目。两组、三模式、每案例每组一次，共 36 次，全部进入分母，不补跑失败、不替换单元，不在运行中改提示、代码或验收。

## 修改

- 默认仍关闭 `repair_quality_checks`。显式启用的新任务冻结 `repair_quality_policy_version=2`；保存的版本 1 继续使用原严格协议，恢复时不静默升级。
- V2 将同一既有源文件的多个编辑按原文唯一锚点、互不重叠范围同时合成一项 Edit，保持中间未修改文本。拒绝重叠、依赖中间状态、歧义锚点、多次新建同一文件和超长组合，不猜测、不逐项顺序应用。既有测试、conftest 和非 Python 文件仍不可改。
- 缺失或纯文字的测试声明由实际新增源码的静态测试定义导出。显式引用不存在的测试/原始测试仍拒绝。源文件引用与模型原始文字单独保留；静态身份不等于语义覆盖，也不等于每项参数化用例已执行。
- 仅用 AST 读取 Issue 点名的 API、签名和默认值，提供受限源代码片段及摘要，补足大文件前缀以外的内容。禁止导入或执行目标代码。最多扫描 128 个源文件、16 个命中 API；每块及总上下文有限，记录截断。摘要对应当前候选修改前基线。
- 审查包区分模型原始声明、从源码导出的测试身份与实际通过的测试证据。三模式保留同一新增测试在原版失败、候选通过的就绪要求；旧行为按原工作流执行。
- 评测器支持两区块 AB/BA，按案例交替起始组，逐区块轮换模式，最多两路案例并发。四区块 V1 ABBA/BAAB 行为保留。

## 验证和解释

安装 wheel 与冻结源码、site-packages 全部应用文件逐字节比对。完整验证在独立复制目录内，以安装包作为父/子进程唯一应用来源运行 pytest，显式启用真实 Docker；原 78 个既有测试/辅助文件与基准提交逐一比较，未改。当前阶段新建的 V1 兼容测试显式冻结策略 1，另以新测试覆盖 V2。

模型使用用户指定通道 `deepseek-v4.1-flash`，生成温度固定为 0。每任务最多 900 秒、8 次模型请求、100000 已观测 Token、6 次产品沙箱、256 MiB 产物及 8 MiB 结果；测试/模型超时均 120 秒、重试 1 次、间隔 7.5 秒、上下文 24000 字符。任务数据与参考/隐藏验收隔离，所有目标代码只在 Docker 执行。密钥只在隐藏输入会话内存，不能进入报告。

本轮最多 288 次新增模型请求；连同首轮实际 190 次，正式请求累计上限 478。此前原生连接诊断 1 次、1215 Token 单列，不计正式修复任务。不新作生成诊断，正式执行前仅验证通道可访问。用量未知保留未知，已记录部分单列，不推断账单。

同一锁定语料与镜像的 24 项原版/参考 Docker 对照复用首轮不可变证据，不能称为本轮新执行。所有原始 Python 测试逐字节保留；统一 pytest/TestCase 适配器没有调用 `unittest.load_tests` 的额外 doctest，三项 JSON Pointer 案例不能声称完整上游原生套件覆盖。不会在这轮中途改变适配器或分母。

主指标仍同时要求：原始测试不变、缺陷基线重现、候选测试通过、独立隐藏验收通过、进入待人工审批。质量组还必须有绑定当前候选的失败到通过证明。两种工作流的证据门槛不同，不能将更多拒绝算作修复能力提升。小规模、相关的确定性交错比较不能证明统计显著、单组件因果或未见项目泛化；第二轮改善也不能覆盖首轮负面结果。保持默认关闭。
